# ADR-0011: Database access: Drizzle and postgres.js over the Supavisor transaction pooler

- **Status:** accepted
- **Date:** 2026-11-04
- **Related:** [ADR-0002](0002-hosting-and-database.md), [ADR-0004](0004-business-logic-in-own-api.md), [ADR-0005](0005-tenant-isolation-rls.md), [ADR-0010](0010-deploy-pipeline-without-staging-deployment.md), F-FOUND-DB, F-TENANT-CORE, F-EVENTS-OUTBOX

## Context
The API runs in Vercel functions (`fra1`). These scale out to many short-lived instances, each of which may open Postgres connections. Supabase's direct connection is IPv6-only and allows few clients. Tenant isolation depends on a tenant context that is set transaction-locally ([ADR-0005](0005-tenant-isolation-rls.md)). Migrations must run from GitHub Actions runners, which use IPv4 ([ADR-0010](0010-deploy-pipeline-without-staging-deployment.md)).

## Decision
At runtime, the app uses Drizzle with the postgres.js driver over the Supavisor **transaction pooler** (`DATABASE_URL`). It sets `prepare: false` and keeps a small, lazily created pool per instance, registered with `attachDatabasePool`. Migrations generated by drizzle-kit run over the **session pooler** (`MIGRATIONS_DATABASE_URL`) through our own `db:migrate` script. All per-request database state is transaction-local.

## Alternatives considered
- **`node-postgres` (`pg`):** a heavier driver with the same pooling constraints, so it gains nothing here.
- **Supabase Data API (PostgREST) over HTTP:** rejected by [ADR-0004](0004-business-logic-in-own-api.md). It provides no transactions for outbox writes.
- **Direct connection:** IPv6-only and one connection per instance; it would exhaust the connection limit under load.
- **Session pooler at runtime:** holds a server connection for each client connection, so it doesn't scale with serverless instances.

## Consequences
- **Positive:** connection count stays bounded under serverless scale-out; transaction-local tenant context works by design; the setup is standard Postgres and can move to another host.
- **Negative / accepted trade-offs:** no prepared statements, session settings, advisory session locks or `listen/notify` at runtime; pool size times instance count must stay under the pooler's client limit.
- **Follow-ups:**
  - The tenant-scoped transaction helper (F-TENANT-CORE) sets context only with `set_config(..., true)`.
  - The outbox dispatcher (F-EVENTS-OUTBOX) doesn't rely on `listen`.
  - The pool size is configurable and is checked in the Stage 7 load test.
