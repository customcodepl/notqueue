# ADR-0013: Database access: Drizzle and node-postgres over the Supavisor transaction pooler

- **Status:** accepted
- **Date:** 2026-11-04
- **Related:** supersedes [ADR-0011](0011-database-access-and-pooling.md); [ADR-0004](0004-business-logic-in-own-api.md), [ADR-0005](0005-tenant-isolation-rls.md), [ADR-0010](0010-deploy-pipeline-without-staging-deployment.md), F-FOUND-DB, F-TENANT-CORE, F-EVENTS-OUTBOX

## Context
[ADR-0011](0011-database-access-and-pooling.md) chose the postgres.js driver and `attachDatabasePool` from `@vercel/functions`, which keeps a Vercel Fluid instance alive until idle connections have been closed. During F-FOUND-DB it turned out that `attachDatabasePool` detects a pool by its `release` event. The `pg` pool emits that event and postgres.js doesn't, so with postgres.js the call silently does nothing. Without it, suspended instances leave idle connections open on the pooler until the pooler times them out. The other forces from ADR-0011 are unchanged: serverless scale-out, an IPv6-only direct connection, transaction-local tenant context, and migrations from IPv4 runners.

## Decision
At runtime, the app uses Drizzle with the node-postgres (`pg`) `Pool` over the Supavisor **transaction pooler** (`DATABASE_URL`). The pool is small and created lazily per instance, and is registered with `attachDatabasePool`. Queries use no named prepared statements. Migrations generated by drizzle-kit run over the **session pooler** (`MIGRATIONS_DATABASE_URL`) through our own `db:migrate` script. All per-request database state is transaction-local.

## Alternatives considered
- **postgres.js without `attachDatabasePool`** (ADR-0011 without the helper): relies on a short client idle timeout and the pooler's timeout, so connections can pile up on suspended instances under load.
- **postgres.js with a custom keep-alive (`waitUntil` until the pool is idle):** re-implements what `attachDatabasePool` already does for `pg`, with no gain.
- **Supabase Data API, direct connection, session pooler at runtime:** rejected for the same reasons as in ADR-0011.

## Consequences
- **Positive:** idle connections are closed before an instance is suspended (the setup Vercel supports); connection count stays bounded; transaction-local tenant context works by design; standard Postgres.
- **Negative / accepted trade-offs:**
  - No named prepared statements, session settings, advisory session locks or `listen/notify` at runtime.
  - Pool size times instance count must stay under the pooler's client limit.
  - `pg` is a larger dependency than postgres.js, which doesn't matter for server-only code.
- **Follow-ups:**
  - The tenant-scoped transaction helper (F-TENANT-CORE) sets context only with `set_config(..., true)`.
  - The outbox dispatcher (F-EVENTS-OUTBOX) doesn't rely on `listen`.
  - The pool size is configurable and is checked in the Stage 7 load test.
